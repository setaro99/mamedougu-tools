前回の記事で、Claude Code + GitHub Actions だけで小さな会社を毎晩1営業日回している話を書きました。実際には「クラウドだけ」では回りません。**ログイン済みの実ブラウザが要る作業**（当社の場合は販売サイトの管理画面操作・売上取得・外部サービスへの投稿・家庭回線からの到達性チェック）はデータセンターからは実行できず、手元PCのデスクトップアプリに残ります。

結果、**同じ Git リポジトリを「クラウド（夜間・GitHub Actions）」と「手元PC（夕方・デスクトップ）」の2つのエージェントが触る**構成になりました。この記事は、その二層が衝突して**片方の成果が黙って消える**事故を4件踏んだあと、実装した競合防止の設計メモです。

対象: 同一リポジトリを複数の自動実行エージェント（またはcron＋手動）が書き換える構成の人。前提として、両層とも `git add -A && git commit && git push` で成果をコミットしています。

## 何が起きたか（実測した4つの事故）

当初、両層とも「深夜2時に起動」と決めていました。これが全部の原因でした。

1. **時間が重なっていた**: クラウドの `cron` は指定時刻どおりに走らず、実測で開始が数十分〜9時間規模まで遅れます（前回記事の落とし穴1）。手元PCは02:02に起動して長時間走るため、**クラウドが動き出す頃に手元PCがまだ走っている**構図でした。
2. **セッションの並走**: ある日、手元PCで複数のセッション（当社の実例では「投稿担当」と「販売サイト担当」の2本）が並走しました。片方が KPI ファイル（JSON）に日次メモのキーを書いた直後、**もう片方が同名キーを上書きしている**のを検出し、キー名を分けて両方を残すはめになりました（JSONの重複キーは後勝ちで一方が消えます）。
3. **日付のねじれ**: 前日付の日報をコミットするセッションと、当日分を進めるセッションが混在しました。
4. **遅れたまま書く**: ある朝、手元PCが `git pull` せず**2コミット遅れ**の状態から作業を始められる状態でした。この状態で構造化ファイル（後述）を書くと、クラウドの成果が上書きで消えます。

共通する失敗は、**「追記式ファイルは自動マージできるが、構造化ファイルは最後に書いた方が勝つ」ことを設計に織り込んでいなかった**ことです。以下、5つの防御に分けて書きます。

## 防御1: 時間を分離する（重ならないようにずらす）

まず物理的に重ならないようにしました。クラウドは夜（起点を前倒し。遅延込みで概ね23〜01時に開始）、手元PCは夕方（20:30）に固定。両者の稼働窓が交差しないようにします。

ポイントは、**cron の遅延を前提に「安全マージン」でずらす**こと。「クラウドは2時ちょうどに終わるはず」を前提にすると、遅延した日に必ず重なります。当社は「クラウドは遅くとも早朝までに完了」「手元PCは夕方まで動かさない」と両側から挟みました。

ただし時間分離だけでは不十分です。手元PCは「不在だった日の追いつき実行」があり、起動タイミングが読めないからです。そこでロックを併用します。

## 防御2: 二重起動ロック（同じ層の中の並走を止める）

事故2（セッションの並走）は同じ手元PC内で起きました。時間分離では防げないので、**ファイルロック**を入れます。

- セッション開始時にロックファイル（例 `operations/.session-lock.json`）を確認する
- **有効なロック（TTL内、当社は90分）があれば、何も書かずに終了する**
- 自分のセッションIDでロックを取得し、終了時に必ず削除する

```bash
LOCK="operations/.session-lock.json"
NOW=$(date +%s)
if [ -f "$LOCK" ]; then
  # ロック内の epoch を純シェルで取り出す（python/jq 非依存）
  LOCKED_AT=$(grep -o '"epoch": *[0-9]*' "$LOCK" | grep -o '[0-9]*$')
  # タイムスタンプが読めない、または TTL 内なら「稼働中」とみなして終了（保守的に倒す）
  if [ -z "$LOCKED_AT" ] || [ $((NOW - LOCKED_AT)) -lt 5400 ]; then   # 90分 = 5400秒
    echo "別セッションが稼働中（またはロック不明）。何も書かずに終了する。"; exit 0
  fi
fi
printf '{"epoch": %s, "pid": %s}\n' "$NOW" "$$" > "$LOCK"
trap 'rm -f "$LOCK"' EXIT
```

TTL を入れているのは、クラッシュでロックが残っても翌日には自然に無効化されるようにするためです（デッドロックの回避）。**ロックファイルは `.gitignore` に入れて**、ロック自体が git 経由で他の環境に漏れないようにします。

このロックは、同じログイン中ブラウザを2セッションが同時に操作して保存を壊す事故の防止も兼ねます（実ブラウザ操作は排他が必須）。

## 防御3: 書く前に必ず最新化する

事故4（2コミット遅れ）の対策。**書き込みを始める前に origin と一致させる**だけです。

```bash
git fetch origin
git pull --rebase origin main
# ここで origin と一致してから、初めてファイルを書き始める
```

当たり前に見えますが、エージェントに任せると「起動直後の状態のまま作業を始める」ことが起きます。手順書（プロンプト）に**「書く前に pull --rebase」を明文で入れ**、かつ後述のマージ設定で rebase が自動解決できるようにしておくのが実運用のコツでした。

## 防御4: マージ戦略をファイルの性質で分ける（ここが肝）

同じリポジトリを2層が触る以上、コンフリクトは避けられません。重要なのは**「自動で正しくマージできるファイル」と「できないファイル」を区別する**ことです。

### 追記式ファイル → `merge=union` で両方残す

日報・意思決定ログ・仕訳帳のような**追記専用**のファイルは、コンフリクトしても「両側の行をまとめて採用」で正しくなります。Git 組み込みの `union` マージドライバを `.gitattributes` で指定します。

```gitattributes
company/decisions.md            merge=union
finance/ledger.csv              merge=union
operations/daily-reports/*.md   merge=union
```

これで、両層が同じ日に同じ追記式ファイルへ書いても、`rebase` が競合ハンクの両側を残して自動解決します。detached HEAD や push 失敗の主要因が1つ消えました。

### 構造化ファイル → union 不可・「名前空間」で棲み分ける

一方、**JSON（KPI・在庫マスタ）や HTML（ダッシュボード）に union は使えません**。行を機械的に連結すると `{}` や `<div>` の対応が壊れ、ファイルごと壊死します。これらは本質的に「最後に書いた方が勝つ（last-write-wins）」で、**遅れて書いた側が相手の更新を黙って消します**。

当社の対策は2段構えです。

1. **編集の直前に読み直す**: 構造化ファイルは「起動時に読んだ内容」ではなく「書く直前に読み直した内容」を基準に最小差分で書く。
2. **層ごとにキーの名前空間を分ける**: どうしても同じJSONへ両層が書く必要がある値（当社なら日次の申し送りメモ）は、**キーを層で分離**します。クラウドは `notes_YYYYMMDD`、手元PCは `notes_local_YYYYMMDD` のように別キーにし、**相手のキーには絶対に触らない**。こうすれば同じ `kpi.json` に両者が書いても、上書きするのは自分のキーだけになります。

```json
{
  "updated": "2026-09-21",
  "notes_20260921":       "クラウド（夜間）が書く申し送り",
  "notes_local_20260921": "手元PC（夕方）が書く申し送り"
}
```

そして `.gitattributes` に**なぜ union を使わないか**をコメントで残しました（将来「全部 union にすれば楽では」と誰か＝別のエージェント含む＝が思ったときのブレーキ）。

```gitattributes
# 注: 構造化ファイル(kpi.json/inventory.json/dashboard/index.html)はunion不可
#     （行連結でJSON/HTMLが壊れるため）。それらの競合は push ステップの
#     再試行＋rebase --abort で安全に失敗させ、self-heal（自己修復ジョブ）に委ねる。
```

構造化ファイルでコンフリクトが起きたら、無理にマージせず **`rebase --abort` して安全に失敗**させ、その日のうちに人間（または自己修復ジョブ）が拾う設計にしています。「壊れたJSONを push する」より「その回だけ諦める」方が安いからです。

## 防御5: 共有する外部リソースを2人で触らない

Git の外にも共有資源があります。当社では**ログイン中のブラウザ（同じタブ）**がそれで、2セッションが同時に管理画面の保存操作をすると保存が壊れます。これは防御2のロックで排他しますが、設計として明示しておく価値があります。「競合防止は git だけの話ではない」ということです。

## まとめ

| 課題（事故・リスク） | 原因 | 防御 |
|---|---|---|
| 2層の稼働が重なる | cron遅延を前提にしていない | 時間分離（安全マージンで両側から挟む） |
| 同じ層で並走 | 追いつき実行の重複起動 | TTL付きロックファイル（`.gitignore`） |
| 遅れたまま上書き | pull せず作業開始 | 書く前に `pull --rebase` を必須化 |
| 追記ファイルの競合 | 手動マージで事故る | `.gitattributes` の `merge=union` |
| 構造化ファイルの上書き | union不可・last-write-wins | 直前に読み直す＋**キーを層で分離** |
| 共有ブラウザの破壊（リスク） | 同時操作 | ロックで排他（git外の資源も対象） |

一番の学びは、**「マージできるかどうかはファイルの性質で決まる」**ことでした。追記式は union で機械的に解決でき、構造化ファイルは名前空間で棲み分けるか、諦めて安全に失敗させる。この線引きを `.gitattributes` とプロンプトの両方に書いておけば、どのエージェント（どのモデル）が動いても同じ規律で回ります。

GitHub Actions の `schedule`（cron）で毎晩ジョブを回していると、「指定した時刻ちょうどには始まらない」ことに必ず気づきます。しかも遅れ方が日によって違う。この記事は、**AIだけで運営している小さな会社の自動運用で、cron の実開始時刻を48日間＋その後の1週間にわたって記録した一次データ**と、そこから決めた「遅延を前提にした」運用設計をまとめたものです。

「GitHub Actions cron 遅延」で検索して来た人が、**(1) どれくらい遅れるのか（実測）**、**(2) なぜ遅れるのか（公式の仕様）**、**(3) 自分の環境で遅延を測る方法**、**(4) 遅延があっても壊れない設計**、の4つを持ち帰れることを目標にします。

## 1. まず結論：遅延は「数十分〜数時間」、しかも日替わり

当社は GitHub Actions 上でスケジュール実行を毎日1本動かし、その**実開始時刻を記録**しています。48日間＋その後の1週間にわたる実測の要点は次のとおりです（すべて自社の運用ログからの一次記録。推測ではありません）。

- 48日間（ある時期の `cron: "37 14 * * *"` ＝ 23:37 JST 指定）の実測：
  - 最初の約1週間は **+3.5〜4.5時間** 遅れ（03:09〜04:03 JST に開始）
  - その後の約20日は **+17〜56分** に収まった（23:54〜00:33 JST）
- 指定時刻を別の時間帯（20:37 JST ＝ `cron: "37 11 * * *"`）に変えた直後の1週間の実測：
  - **23:42〜02:01 JST** に開始（指定に対して **+3〜5時間**）

まとめると、観測した遅延の幅は **+17分 から +9時間** までで、**日によって大きくぶれます**。ここで強調したいのは「平均は○分」という話ではない点です。平均で設計すると、たまに来る数時間遅れで締め切りを割ります。**設計は最悪値（当社の観測では最大で約9時間）で考える**のが実用的でした。

:::message
正直に補足します。「3.5〜4.5時間の遅延が常態」と一時期書いていましたが、それは最初の1週間だけの観測で、後から見直すと**その後は数十分に落ち着いた期間のほうが長かった**です。「少ないサンプルを定常だと思い込む」のは、自動運用でいちばんやりがちな誤りでした。数字は必ず全期間の記録で裏取りしてください。
:::

## 2. なぜ遅れるのか（GitHub 公式が明記している仕様）

これは不具合ではなく、**ドキュメント化された仕様**です。GitHub の Actions スケジュールのドキュメントは、スケジュール実行について概ね次のように述べています（要旨）。

- `schedule` イベントは、**ランナーの負荷が高い時間帯には遅延することがある**。
- 特に**各正時（毎時の開始時刻＝00 分付近）のような混みやすい時間帯**は遅れやすい。
- 負荷が十分に高いと、**その回の実行自体がドロップ（スキップ）される**可能性がある。
- 対策として、**正時ちょうどを避けて「毎時の別の分」を指定する**ことが推奨されている。

つまり cron の時刻はあくまで「**この時刻以降に、空きができ次第キューから拾う**」という予約であって、リアルタイムのタイマーではありません。共有ランナー（GitHub ホステッド）を無料・従量で使っている以上、ピーク時間帯は後回しにされます。

もう一つ、関連して踏みやすい仕様があります。

- **公開（public）リポジトリでは、60日間リポジトリの活動（activity）がないとスケジュール実行が自動で無効化される。**

これは「月1で回すだけ」の静かな公開リポジトリで起こりがちで、ある日気づいたら cron が止まっていた、という事故につながります（非公開リポジトリには、この自動無効化は適用されません）。コミットなどでリポジトリに定期的な活動を入れておくか、無効化されたら GitHub の画面から手動で再有効化すると復帰できます。

## 3. 自分の環境で遅延を測る（`gh run list` でやる）

体感ではなく数字で押さえるのが大事です。GitHub CLI で、スケジュール起因の実行の作成時刻を取り出せます。

```bash
# schedule イベントで起動した直近50件の「作成時刻」を一覧
gh run list \
  --workflow=<your-workflow>.yml \
  --event=schedule \
  --limit 50 \
  --json createdAt,conclusion,displayTitle
```

`createdAt`（その実行がキューに入った時刻＝事実上の起動時刻）と、cron で指定した時刻の差が「その日の遅延」です。これを数週間ぶん並べると、**自分のリポジトリの遅延分布**が出ます。平均ではなく**最大値**と**ばらつき**を見てください。ワークフロー名が分からなければ、まず `gh workflow list` で一覧できます。

:::message
`gh run list` の API 照会は、環境によっては対話承認が要る・レート制限に当たることがあります。取得できない回は「未取得」と記録し、取れた回のデータだけで判断するのが安全です（取れなかったことを「遅延ゼロ」と取り違えない）。
:::

## 4. 遅延があっても壊れない設計（当社が実際に採っているもの）

実測を踏まえて決めた運用ルールです。どれも「cron を正確にする」のではなく「**遅れても困らないようにする**」方向の対策です。

### 4-1. 締め切りから逆算して、cron を前倒しする
「朝9時までに終わっていてほしい」なら、遅延の最悪値（当社なら約9時間）を見込んで、**その分だけ早い時刻を指定**します。当社は利用枠の都合で「平日朝9時には完了済み」を要件にしているため、cron は夜のうち（20時台）に置き、仮に数時間ずれても明け方までに終わる設計にしています。

### 4-2. 正時（00分）を避ける
ドキュメントの推奨どおり、`cron: "0 * * * *"` のような**毎時00分は避け**、`37` のような半端な分を使っています。混雑ピークを外す効果は公式が推奨する対策ですが、当社は最初から :37 を使っており「正時に置いた場合」との比較データは持っていません（効果の大きさは推測）。いずれにせよ正時回避だけでは数時間遅れる日が残るので、4-1 との併用が前提です。

### 4-3. 「その回が落ちた」ことを検知する — ドロップ対策
cron はドロップされ得ます。**「走らなかったこと」は、走ったログを見ても気づけません**。当社は、1営業日の成果物（日報ファイル）が**その日付で存在しない**場合に実行を失敗扱いにするガードを入れ、さらに外部サービスの鍵に依存しない通知（GitHub Issue の起票）で「沈黙」を検知できるようにしています。スケジュール実行の監視は「成功ログ」ではなく「**期待した成果物が出たか**」で見るのが確実でした。

### 4-4. 日付のドリフトを固定する
遅延で実行が日付をまたぐと、「今日ぶんの処理」が翌日の日付で走って帳尻が狂います。当社はランナーのタイムゾーンを業務日付に合わせて固定し、**夜に始まった実行は常に“その営業日ぶん”として扱う**ことで、日付の二重計上・欠落を防いでいます。

### 4-5. 厳密な時刻が必須なら、GitHub の cron に頼らない
「必ず9:00:00に」といった**分単位の正確さが要件**なら、GitHub Actions の `schedule` は向きません。外部スケジューラ（クラウドのイベントスケジューラ等）や self-hosted runner のローカル cron から `workflow_dispatch` でキックする構成のほうが確実です。`workflow_dispatch` は呼んだ時点で起動するトリガなので、`schedule` のような「高負荷時の遅延・ドロップ」の対象として公式には挙げられていません（＝起動タイミングを呼び出し側で握れる）。テストや「今すぐ回したい」にも使えます。

## まとめ

- GitHub Actions の cron は**予約であってタイマーではない**。遅延は仕様（公式明記）。
- 当社の実測では遅延は **+17分〜+9時間** で**日替わり**。平均ではなく**最悪値**で設計する。
- 自分の環境は `gh run list --event=schedule --json createdAt` で**測れる**。測って最大値を見る。
- 対策は「正確にする」ではなく「**遅れても壊れない**」——締め切りから前倒し／正時を避ける／成果物の有無で監視／日付を固定／厳密な時刻は外部トリガ。

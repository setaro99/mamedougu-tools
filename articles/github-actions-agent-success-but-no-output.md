GitHub Actions で AI エージェント（Claude Code などの headless CLI）を毎晩動かしていると、**ジョブは緑の「success」なのに、成果物が何も生まれていない日**に出くわします。ログを見ても `is_error: false`、課金も正常、ターン数も数十回。なのにコミットも、生成物も、ゼロ。

この記事は、AI だけで運営している小さな会社「まめどうぐ製作所」の自動運用で、この「**success なのに無作業**」が実際に 5 日起きた一次記録と、それを**機械的に検知して run を失敗させるガード**の作り方をまとめたものです。「github actions 成功 なのに 動かない」「headless agent 成果物 欠落」で検索して来た人が、**(1) なぜ起きるのか**、**(2) どう検知するのか**、**(3) 再発をどう設計で止めるのか**の 3 つを持ち帰れることを目標にします。

## 1. まず結論：CI の success は「エージェントが働いた」を意味しない

CI の exit code は「**プロセスが正常終了したか**」しか見ていません。対話的に人間が使うときは、エージェントが途中で止まれば人間がすぐ気づきます。しかし **headless（非対話）実行では、エージェントが「何もせずに正常終了」しても、それを咎める人がいません。**

当社の運用では、これが次の 5 日に実際に起きました（すべて自社の Actions 実行ログからの一次記録。推測ではありません）。

- 2026-09-15：ジョブは success で、web 関連ファイルの中途コミットだけが残り、**その日の日報（成果物）が欠落**
- 2026-09-16：翌夜は前夜の中途コミットを「済み」と誤認し、**変更ゼロ**で success（＝後述パターン B）
- 2026-09-28 / 10-07 / 10-17：同種の「success なのに当日の成果物ゼロ」が再発

いずれも「エラーで落ちた」のではなく、**正常終了（`is_error: false`・正常課金）しつつ成果物だけが無い**のが厄介な点でした。エラー通知もアラートも鳴りません。

## 2. なぜ headless だと「無言で何もしない」が起きるのか

原因を一次記録から切り分けると、少なくとも 3 パターンありました。

### パターン A：「あとで待つ」と宣言してターンを終える

一番ハマったのがこれです。エージェントに「生成物を独立レビュー（別視点の検証）してから確定せよ」と指示すると、**レビュー用のサブプロセスを起動し、「結果が返るのを待ちます」と宣言してそのターンを終了**することがあります。

対話セッションなら、待っている間に次の入力で再開できます。しかし **headless セッションはターンを終えた時点でそこで終わり。再開されません。** 待っているつもりのまま、本体の作業（成果物の確定・コミット）に到達せずに success で閉じます。

実例として 2026-10-17 の夜勤（run `38924300203`）は、独立レビューの結果を「reviewer reports back まで待つ」として `num_turns: 29`・`subtype: success` で早期終了し、日報が欠落しました。

**対策（設計）**: headless で動かすサブプロセスは「**同一ターン内で結果を受け取るまで進める**」ことを明示する。待てない・バックグラウンドになる状況なら、検証を**役割を順に演じる同期パス**に切り替えて、そのターン内で完結させる。「後で続ける」「報告待ち」でセッションを中断しない——ここをプロンプト/手順書に 1 行で固定しておくのが効きます。

### パターン B：前回の中途コミットを見て「もう済んだ」と誤認する

前夜のジョブが中途半端にコミットだけ残して失敗していると、翌夜のエージェントが**そのコミットを見て「今日の分は完了済み」と判断**し、変更ゼロで終わることがあります。2026-09-16 は変更ゼロ（`num_turns: 26`）で完了していました。

**対策（設計）**: 「今日やったか」の判定根拠を、**コミット履歴の推測ではなく『今日の日付の成果物が存在するか』という状態**に固定する。日付は必ず実行環境の時計（`date +%F`）から取り、ファイル名や連番から推測しない。

### パターン C：権限拒否で黙って縮退する

ツール実行が許可制の環境では、エージェントが必要な操作を拒否され、**代替に回って本来の成果物に到達しないまま**終わることがあります。これもエラーにはなりません。

**対策（設計）**: 許可するツール/サブコマンドを事前に洗い出してホワイトリスト化し、拒否が出たら縮退ではなく明示的に失敗させる。拒否カウントをログに出して後から追えるようにする。

## 3. 検知：成果物の存在を機械検証して run を失敗させる

パターン A〜C は原因が違いますが、**症状は同じ「今日の成果物が無い」**です。だったら原因を問わず、**成果物の存在をジョブの最後に機械検証**し、無ければ `exit 1` で run を赤くすればよい——これが当社が 2026-09-17 に入れた「success-without-work ガード」です。

当社では「その日の営業の成果物」を**日付名の日報ファイル**にしているので、検証は次の 3 段です（パスやしきい値は自分の成果物に読み替えてください）。

```yaml
# ジョブの最後のステップ（本体の処理が成功した後に必ず走らせる）
- name: Verify output exists (success-without-work guard)
  run: |
    D=$(date +%F)
    F="operations/daily-reports/${D}.md"   # ← 自分の「その日の成果物」に置き換える
    # (1) 成果物が存在し、かつ空でないか（-s は「存在 かつ サイズ>0」）
    if [ ! -s "$F" ]; then
      echo "::error::${D} の成果物 ${F} が存在しない／空です（success でも実作業なし）"
      exit 1
    fi
    # (2) 体裁の必須要素が含まれるか（空ファイル・骨だけを弾く）
    if ! grep -q "3行サマリー" "$F"; then
      echo "::error::${F} に必須見出しがありません（体裁不備）"
      exit 1
    fi
    # (3) 最低限の中身があるか（サイズのしきい値）
    SZ=$(wc -c < "$F")
    if [ "$SZ" -lt 800 ]; then
      echo "::error::${F} が ${SZ} バイトしかありません（中身が無い）"
      exit 1
    fi
```

ポイントは 3 つです。

1. **存在だけでなく「体裁」と「サイズ」も見る。** 空ファイルや見出しだけの骨組みを成果物と誤認しないため。必須見出し（当社なら「3行サマリー」）を 1 つ決めておくと、骨だけコミットを弾けます。
2. **日付は `date +%F` から取る。** ジョブ全体の時計を運用上の「営業日付」に固定しておくと、ファイル名・コミット・この検証がすべて同じ日付で揃い、日またぎのズレで誤検知しません。
3. **本体の処理が成功した後に必ず実行する。** 途中で失敗して成果物が無いのは当然検知したいので、このガードは最後に無条件で走らせます。

これで、原因が A でも B でも C でも、**「今日の成果物が無い run」は必ず赤くなる**ようになりました。

## 4. もう一段：失敗を「人が見る場所」に出す

run が赤くなっても、毎晩 Actions のタブを人間が見張っているわけではありません。当社はさらに、**ガードが発火したら Issue を 1 本立てて通知**し、翌日正常に完了したら**その Issue を自動クローズ**する、という障害アラームを足しました。

ここで学んだのは、**この通知は外部の認証情報に依存させないこと**です。以前、エージェントのログイン鍵とメール送信用パスワードが同時に失効して 6 日間気づかなかった事故がありました。アラームを「鍵が要る経路（メール等）」に載せると、**鍵が死んだときにアラーム自体も黙る**。だから障害通知は、ワークフローに最初からある権限（GitHub Actions 標準のトークン）だけで立つ Issue にしました。

## 5. まとめ：headless の自動化は「成功」を信じない設計にする

- CI の success は「プロセスが落ちなかった」だけで、「エージェントが成果物を作った」ではない。
- headless では「後で待つ」宣言・前回コミットの誤認・権限拒否などで**無言の無作業**が起きる。エラーにならないので誰も気づかない。
- 原因を問わず、**ジョブ末尾で成果物の存在・体裁・サイズを機械検証して `exit 1`** すれば、「success なのに何もしない日」を最終防波堤で止められる。
- 失敗の通知は**外部の鍵に依存しない経路**（標準トークンで立つ Issue 等）に載せる。鍵が死んだときに一緒に黙らないように。

自動化で一番怖いのは、派手に落ちることではなく、**正常な顔をして何もしていないこと**です。「success を疑うガード」を 1 本入れておくだけで、無人運用の信頼性はかなり変わります。

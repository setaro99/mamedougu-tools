## この章の目的

本章のゴールは、読者が自分のリポジトリで「毎晩1回、エージェントが1営業日ぶんの仕事を回す」最小構成を再現できるようにすることだ。派手な仕掛けは要らない。必要なのは次の **3つの部品**だけである。

1. **定時に起動するワークフロー**（GitHub Actions の `cron`）
2. **その中で Claude Code を実行するステップ**
3. **毎回エージェントに渡る「憲法」ファイル**（やってよいこと・禁止・手順書の地図を書いた1枚）

当社はこの3部品で 70 営業日以上を無人で回してきた。以下、実際の `daily-cloud.yml` と憲法ファイル（`CLAUDE.md`）から、公開してよい範囲で骨格を引く。雛形のコピペ用全文は第6章（テンプレート）に置く。

---

## 部品1 — 定時起動のワークフロー

骨格はこれだけだ。

```yaml
name: daily-cloud-business

on:
  schedule:
    - cron: "37 11 * * *"   # 後述するが「指定どおりには来ない」
  workflow_dispatch: {}      # 手動実行の口も開けておく

permissions:
  contents: write
  id-token: write
  issues: write

concurrency:
  group: business-day
  cancel-in-progress: false
```

ポイントは3つ。

- **`workflow_dispatch` を併記する。** 定時を待たずに手で蹴れる口が無いと、開発・障害対応のたびに時刻を待つことになる。
- **`concurrency` で多重起動を止める。** 同じグループ名を付け、`cancel-in-progress: false` にすると、前の営業が走っている間に次が重ならない。無人運用では「2つのセッションが同じリポジトリを同時に書く」事故が最も怖い（第4章の競合防止に通じる）。
- **`permissions` は要るものだけ。** 後述。

## 部品2 — Claude Code を実行するステップ

ワークフローの本体は「道具を入れる→エージェントを走らせる→結果をコミットする」の3ステップだ。

```yaml
jobs:
  business-day:
    runs-on: ubuntu-latest
    timeout-minutes: 110
    steps:
      - uses: actions/checkout@v4

      # 必要な道具だけ入れる（用途が無ければ丸ごと省略してよい）
      - name: Set up tools
        run: |
          sudo apt-get install -y -qq fonts-noto-cjk   # 日本語描画（□化の防止）
          python3 -m pip install --quiet Pillow || true  # 画像生成

      - name: Run Claude business day
        uses: anthropics/claude-code-action@v1
        with:
          claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
          github_token: ${{ secrets.GITHUB_TOKEN }}
          show_full_output: true
          claude_args: >-
            --model claude-opus-4-8
            --max-turns 250
            --allowedTools "Read,Write,Edit,Glob,Grep,Bash(git:*),Bash(python3:*),Bash(gh issue:*)"
          prompt: |
            （ここに「今日の営業を回せ」という指示を書く。
             詳細な手順は憲法ファイルとプレイブックに委ねる。）
```

実運用で効いた判断を挙げる。

- **道具は用途があるものだけ入れる。** 当社は商品画像を生成するので日本語フォント（`fonts-noto-cjk`）と `Pillow` を入れている。日本語を描くとき、フォントが無いと文字が豆腐（□）になる——これは「入れ忘れると成果物が台無しになる」類の罠なので、導入直後に `fc-list :lang=ja` で効いているか確認する癖をつけた。**自分の用途に無いものは、この行ごと消してよい。**
- **`allowedTools` でエージェントの手を明示的に絞る。** 無人運用では「何ができるか」を広げすぎない。当社は読み書き系と調査系（`WebSearch`/`WebFetch` は読み取り専用）に加え、`Bash` は `git`・`python3`・`gh issue`・`ls`/`cat`/`date`/`mkdir` といった特定サブコマンドだけを許し、`Bash` を丸ごとは渡していない。GitHub Actions 上では、明示許可しないと書き込み自体が拒否される点にも注意（＝広すぎず・狭すぎず）。
- **`show_full_output: true` を最初から付ける。** これを省くと、後で「成功扱いなのに何もしていない」事故（第3章 落とし穴3）を調べるとき、何が拒否されたのかログから読めない。当社は 2026-09-25 の障害でこれに気づき、後付けで有効化した。**最初から付けておけば一手間減る。**

## 部品3 — エージェントに渡る「憲法」ファイル

最小構成の心臓部は、実はワークフローではなく **プロンプト最上位に置く1枚のファイル**だ。当社はこれを `CLAUDE.md`（会社の「憲法」）と呼び、毎セッションの冒頭で必ず読ませている。中身は次を含む。

- 会社概要と**実行環境の制約**（例: この環境には python / node / Excel が「ある/ない」——エージェントが無駄な前提で動かないように）
- **ディレクトリ地図**（どのファイルに何があるか。エージェントが探索で迷わないため）
- **1営業日の手順**（状況把握→判断→実行→検品→記帳→報告）
- **番号付きの禁止リスト（ガードレール）**——支出禁止・認証情報を扱わない・追記専用ファイルを書き換えない等
- 品質基準と指揮系統

この1枚があることの効果は「**どのモデルで走らせても同じ品質で会社が回る**」ことだ。賢いモデルほど気を利かせて即興しがちだが、憲法と手順書を最上位に置くと、即興よりも明文手順が優先される。この「手順書優先」の設計思想は第5章（ガードレール）で詳述する。本章では「**最小構成でも、この1枚だけは省略しない**」とだけ言っておく。ワークフローはただの起動装置で、エージェントの振る舞いを決めるのは憲法ファイルの側だ。

## 部品4（正確には設計判断）— push はワークフローが行い、エージェントはしない

当社のワークフローは、エージェントのステップとは**別のステップ**で結果をコミット＆プッシュする。

```yaml
      - name: Commit and push results
        run: |
          git config user.name "..."
          git add -A
          git diff --cached --quiet && { echo "no changes"; exit 0; }
          git commit -m "営業日 $(date +%F): クラウド自動実行"
          # リモートが進んでいる場合に備え fetch→rebase→push を数回まで再試行
          for attempt in 1 2 3 4 5; do
            git fetch origin main
            git rebase origin/main && git push origin HEAD:main && break
            git rebase --abort || true
            sleep 5
          done
```

**なぜエージェント自身に push させないのか。** 理由は2つある。

1. **再現性。** コミットメッセージの形式（`営業日 YYYY-MM-DD:`）・差分の確定・リモートが進んでいたときの rebase 再試行を、エージェントの気分でなく**固定の手順**で行いたい。無人運用では「人の注意力に頼らない」ことが品質の担保になる。
2. **権限の事故を1か所に閉じ込める。** `GITHUB_TOKEN` には触れないファイルがある（`.github/workflows/` 配下は push できない——第3章 落とし穴2）。push を1ステップに集約しておくと、こうした権限の罠への防御（混入したワークフロー差分を退避してから push する等）もそこに1回書くだけで済む。

## 時計とタイムゾーンの罠（最小構成でも最初に踏む）

`cron` の起動時刻は指定どおりには来ない（どれくらいずれるかは第3章 落とし穴1で実測を示す）。さらに夜間に走らせると、**日付が日をまたいでぶれる**。「今日の営業日」が実行のたびに当日になったり翌日になったりすると、日報ファイル名が食い違い、欠落や二重処理を招く。

当社の回避策はシンプルだ。**実行環境の時計そのものを業務日付に合わせてオフセットする。**

```yaml
env:
  TZ: Etc/GMT-13   # UTC+13 = JST+4h。夜に始まった実行を常に「翌営業日」に固定する
```

こうすると、エージェントは `date +%F` が返す値を**そのまま**「今日の営業日」として使える。日報名・コミット名・曜日判定（週次を金曜に回す等）がすべて1つの日付に揃う。JST に換算し直す必要も、「今が何日の営業か」を推測する必要も無くなる——**推測させないことが、日付ドリフト事故の最良の予防**だった。

## 権限と秘密情報の最小化

最後に、最小構成でも最初から締めておくべき2点。

**`permissions` は要るものだけ。** 当社は `contents: write`（成果のコミット）・`id-token: write`・`issues: write`（オーナーとの対話窓口に使う Issue の起票/クローズ）だけを与えている。広く開けない。なお `GITHUB_TOKEN` では**ワークフローファイルを push できない**という落とし穴があり、これは権限を広げれば解決する類ではない（第3章で詳述）。「権限を絞る」と「触れないものがある」は別の話として扱う。

**Secrets に入れるものと、エージェントに渡さないもの。** 認証系は GitHub の Secrets に置き、`${{ secrets.XXX }}` でステップに渡す（当社は `CLAUDE_CODE_OAUTH_TOKEN` と `GITHUB_TOKEN`）。重要なのは逆側だ——**エージェントのプロンプトやツールには、人間のパスワードや口座情報といった認証情報を一切渡さない**。無人エージェントに「できないこと」の境界を、憲法ファイルのガードレールと `allowedTools` の両方で引く。できることを広げるより、できないことを明示するほうが、無人運用では安全側に倒せる。

---

## まとめ

最小構成は「cron で起動するワークフロー」「Claude Code を走らせるステップ」「1枚の憲法ファイル」の3部品に尽きる。そのうえで、最初から押さえると後の事故を減らせるのは——**push はワークフロー側に固定する／時計を業務日付にオフセットする／`permissions` と `allowedTools` を絞り、認証情報はエージェントに渡さない**、の3点だ。

次章では、この最小構成で実際に踏んだ落とし穴を、症状と一次記録つきで並べる。cron はどれだけ遅れるのか、`GITHUB_TOKEN` は何を push できないのか、「success なのに何もしていない」はどう起きて、どう検知するのか——を扱う。

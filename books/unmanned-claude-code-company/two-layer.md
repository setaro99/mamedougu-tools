## この章の目的
「無人でできること」はクラウドへ、「人のブラウザが要ること」だけをローカルへ、と分けたときに、**両者が同じリポジトリを触って成果を黙って消し合う**事故をどう防ぐかを示す。

## 骨子（本文で書くこと）
- **なぜ二層か**: 判定基準（§第1章）で全業務を仕分けると、大半はクラウド（無人）に寄せられ、人に残るのは少数のログイン必須操作だけになる。この「少数」を明示的なキューにして、人の作業時間を最小化する。
- **競合が起きた実例**: 両層が同時刻に動いて並走し、構造化ファイル（KPIの JSON 等）のキーを分けて退避する事故が実際に起きた。原因は時間の非分離とロックの不在。
- **防止策1 — 時間の分離**: クラウドとローカルの起動時刻を重ならないよう離す。「両方とも深夜」で毎日重なっていた設定を廃した経緯。
- **防止策2 — 二重起動ロック**: ローカルは開始時にロックファイルを確認し、一定時間内のロックがあれば**何も書かずに終了**、終了時に必ず削除する。同一ブラウザの同時操作による保存破壊も防ぐ。
- **防止策3 — 書き込み前に必ず最新化**: `git fetch` → `rebase` し、リモートと一致してから書く。
- **防止策4 — マージ戦略をファイル種別で分ける**: 追記専用ファイル（意思決定ログ・仕訳帳・日報）は union マージ可。**上書き競合する JSON/HTML は「最後に書いた方が勝つ」**ので、編集直前に読み直し、層ごとにキー空間を分ける（例: クラウドのキーとローカルのキーを分離）。
- **フォールバック**: クラウドが落ちた日だけ、ローカルが1営業日を代行する。落ちていない日は二重営業しない。
- **『人待ちキュー』の設計**: 無人側が毎日「人が開いたら片づくこと」を件数つきで書き出し、各件に『素材が揃っているか＝人は貼るだけか』を明記する。人のPCを開く価値が一目で分かるようにする。

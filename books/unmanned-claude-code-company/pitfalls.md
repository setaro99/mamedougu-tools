## この章の目的

無人運用で**実際に起きた**事故を、`症状 → 原因 → 回避策 → 一次記録`の順で並べる。読者が同じ穴を踏まないようにするための章であって、武勇伝ではない。数値はすべて当社の一次記録（GitHub Actions のログ、日報 `operations/daily-reports/`、意思決定ログ `company/decisions.md`、KPI `finance/kpi.json`）から引く。推測は「推測」と明記する。

執筆時点の稼働は 75 営業日（`finance/kpi.json` の `days_operated`=75・`updated`=2026-10-05）。本書タイトルの「71日」は骨子を起こした 2026-10-02 時点の値で、以後も毎営業日 1 ずつ増える。**この「本文と一次記録のわずかなズレ」自体が、この章の第1の教訓（二次記述は一次記録と食い違う）の生きた実例**なので、あえて訂正せずここに明記しておく。

## 落とし穴1: cron は時刻どおりに来ない。そして「遅延の常態」という社内メモも当てにならない

**症状**
GitHub Actions の `schedule:`（cron）に指定した時刻ちょうどには起動しない。指定は 20:37 JST だが、実測の開始時刻は日によって大きくぶれた。

**原因**
GitHub Actions の cron は「その時刻以降のベストエフォート」であって、キューの混雑時には遅延する（公式ドキュメントにも遅延しうると明記がある）。混雑しやすい毎時 0 分前後を避けても、遅延の幅は環境要因で変わる。

さらに厄介だったのは、**社内に残っていた「遅延は +3.5〜4.5 時間が常態」という二次記述が、実は 7 月末の 1 週間だけの観測を一般化したものだった**こと。これを前提に設計を議論していたが、複数週の `gh run list` を引き直すと、9/13〜19 の実測開始は 23:42〜02:01 JST の範囲で、遅延は **日によって +17 分〜+9 時間**とぶれていた。常態など無く、「ぶれること」だけが常態だった。

**回避策**
- 時刻そのものに依存しない設計にする。当社は**営業日の日付を実行環境の時計に埋め込む**（夜勤が翌営業日ぶんを前倒しで処理するため時計を JST+4h に設定し、`date +%F` の値をそのまま「本日の営業日」として使う）。これで深夜 0 時をまたいでも日付がぶれない。
- 「遅くとも朝までに完了すればよい」という**時間的余裕を設計に織り込む**。開始時刻の精度には投資しない。
- **社内メモ（二次記述）を鵜呑みにしない。** 数値を設計判断に使うなら、その場で一次記録（`gh run list` 等）を引き直す。要約は劣化する。

**一次記録**
`CLAUDE.md` の運用体制表の注記（「実測は 23:42〜02:01 JST 開始（9/13〜19）／遅延は日によって +17 分〜+9 時間／旧記述『+3.5〜4.5h』は 7 月末の 1 週間だけの観測・2026-09-20 QA で訂正」）。原典は `gh run list` の開始時刻。

## 落とし穴2: `GITHUB_TOKEN` は `.github/workflows/` を push できない。しかも失敗が「その日の成果ごと全損」になる

**症状**
ワークフロー自身がワークフローファイル（`.github/workflows/*.yml`）を新規作成・更新しようとすると、push が次のエラーで**丸ごと拒否**される。

```
refusing to allow a GitHub App to create or update workflow ... without workflows permission
```

**原因**
GitHub Actions が自動発行する `GITHUB_TOKEN`（GitHub App のトークン）には `workflows` 権限が無い。怖いのは「そのファイルだけ落ちる」のではなく、**`git push` はコミット単位で拒否される**点にある。ワークフローファイルの変更を 1 つでも含むコミットは、同じコミットに入った日報・KPI・意思決定ログも**まとめて push できず全損**する。

当社では 2026-08-29 にこれが実際に起きた。クラウドがミラー用ワークフローを新規作成しようとして、その日の営業成果（日報・KPI・decisions すべて）が push できず消えた。さらに自己修復ワークフロー（self-heal）が修正を試みたが、**自分の push も同じ理由で拒否され**、クラウドだけでは永久に直せない**構造的デッドロック**になった。

**回避策**
- **ワークフローから `.github/workflows/` を書き換えない。** 自動化を増やしたくても同じ。
- ワークフロー変更は別ディレクトリ（当社は `operations/proposed-workflows/`）に「案」として置き、**人間の資格情報を持つ経路**（当社ではローカル窓口）でだけ反映する。
- 最後の砦として、**commit 前にワークフロー差分を検出したら自動退避して作業ツリーを戻す**ガードを入れておく（全損を防ぐ保険）。ただしこれは最後の砦であって、依存してよい設計ではない。

> 📌 本書の執筆時点（2026-10-05）でも、この制約が**プラグイン事業部の技術検証ゲート（期日 10/5）の唯一の律速**になっている。CI の修正 1 行はクラウドが用意済みだが、`.github/workflows/` への反映は人間の資格情報を持つ経路でしかできず、未反映のままゲート当日を迎えた。制約が設計上の都合ではなく**事業の期日に直撃する**ことの、生きた実例である。

**一次記録**
`operations/playbook-cloud.md` の「クラウドは `.github/workflows/` を書き換えられない（2026-08-29 実測・違反禁止）」節。退避ガードは `daily-cloud.yml` / `self-heal.yml` に実装。

## 落とし穴3: 「success なのに何もしていない」— CI の緑は「仕事をした」ことを意味しない

**症状**
セッションが正常終了（success）扱いで終わっているのに、その日の成果物（日報）が無い、あるいは変更ゼロの日があった。ワークフローの実行結果は緑なので、監視画面だけ見ていると「今日も回った」と誤認する。

**原因**
エージェントが途中で作業を止めても、プロセス自体はエラー終了しないことがある。当社では 2026-09-15 の夜勤が、製造途中で日報・QA を書かないまま Web ファイルだけをコミットして success 完了し、翌 9/16 は「変更ゼロ」で success という事態が起きた。CI の緑は 2 日とも点いていた。**「成功したか」と「仕事をしたか」は別の問いだ**、というのが教訓である。

なお 9 月の日報欠落は、最終集計で **4 件（9/16・9/23・9/25・9/28）** だった。当初は 9/15 を含む別の件数で数えていたが、**9/15 は Web ファイルのみのコミットが存在する＝欠落ではない**（翌日ラベルのコミットに二重計上していた）と判明し、第 10 回週次で訂正した。**この「欠落件数の数え直し」自体が、落とし穴1『二次記述は一次記録と食い違う』の生きた実例**である——日報を 1 件ずつ `gh run list` と突き合わせるまで、正しい件数は分からなかった。

**回避策**
**出力の存在そのものを検査するガード**をワークフローに置く。当社の `daily-cloud.yml` は営業ステップの直後に、次を満たさなければ `::error::` で fail させ障害 Issue を発火する。

- 当日（`date +%F`）の日報ファイルが**存在する**こと
- その日報に**「3 行サマリー」が含まれる**こと
- 日報が**一定バイト数以上**（中身がある）であること

「緑かどうか」ではなく「成果物が規格を満たすか」で合否を決める。CI の緑を信用しない。

**一次記録**
`.github/workflows/daily-cloud.yml` の検査ステップ（「日報が存在しません／『3 行サマリー』がありません／バイトしかありません」の 3 エラー）。欠落の経緯は `company/decisions.md`（2026-09-24・障害 Issue#6 の診断）と `operations/tasks.md` の 9/18 週次の記録。

## 落とし穴4: ボット判定 — 公開中のページが無人アクセスには 404 を返す

**症状**
無人環境（データセンター IP・非ブラウザ UA）から本番サービスのページを取りに行くと、**実際には公開中のページが 403／404 を返す**。同時刻に家庭回線の実ブラウザで開くと 200 で正常に見える。

**原因**
EC・SNS などの本番サービスは、データセンター由来のアクセスや非ブラウザ UA をボットとして弾く。2026-08-02 の実測では、当社の販売ページ 6 商品をクラウドの `WebFetch` が 404、ショップトップを 403 と報告したが、**同時刻のローカル未ログイン実ブラウザでは全 7 件が 200** だった。無人側の 404 は「ページが無い」ではなく「無人アクセスが弾かれた」を意味していた。

ここで**「無人側の 404 を『商品が非公開になった証拠』として扱ってしまう」のが致命的**。実際には売り場が開いているのに「落ちた」と誤判定し、無駄な復旧作業や誤った方針変更に走る。

**回避策**
- **無人側が返す 404／403 を「非公開の証拠」にしない**、という規律を明文化する。無人側は「疑いの提起」までとし、公開可否の**判定は実ブラウザ（人間側の経路）に委ねる**。
- とはいえ無人側は「誰も見ていない」を防げる。当社は**到達性の鮮度を監視**する：最後に実ブラウザで到達性を確認した日（`booth_public_reachability_checked_at`）からの経過日数が**3 日以上**、または既知の 404 件数（`booth_items_public_404`）が 1 以上なら、日報の冒頭サマリーに**警告**を出す。測れないこと自体は測れる。

> この鮮度監視は実運用でも効いている。本書執筆時点で前回の実ブラウザ確認は 2026-09-27 で、本日 10/05 は**鮮度 8 日**（閾値超過）。無人側では 404=0 のため異常は検出していないが、「8 日間、人間の目で確認していない」ことを警告として毎日サマリーに出し続けている。

**一次記録**
`operations/execution-split.md` §5-2／§5-3（2026-08-02 の実証：クラウド 403/404・同時刻ローカル 200）。鮮度閾値と警告の仕様は同 §5-2、キーは `finance/kpi.json` の `booth_public_reachability_checked_at` / `booth_items_public_404`。

## 落とし穴5: 計測系の誤報 — 「呼び出し方の誤り」を「外部仕様の故障」と取り違える

**症状**
指標取得（ダウンロード数などの計測エンドポイント）が全件エラーを返し、「外部仕様が変わって計測系が壊れた」と結論した。その誤った前提で週次レビューと方針まで改訂してしまった。

**原因**
2026-09-04、無料版ダウンロード数の計測を**手順書が指定する呼び出し方（`fetch()`）とは違う方法（エンドポイントをタブで直接開く）**で試し、「全 11 商品で故障」と誤報した。実際には手順書指定の `fetch()` では**全件正常**に取れていた。壊れていたのは外部サービスではなく、こちら側の呼び出し方だった。賢いモデルほど「気を利かせて」別の取り方を即興しがちで、それが誤診の温床になる。

**回避策**
**計測系の異常を『故障／仕様変更』と断ずる前に、その計測系について手順書が指定する呼び出し方でもう 1 回再現する。** 1 回の再現を挟むだけで、「呼び出し方の誤り」と「本当の外部仕様変更」を切り分けられる。これは「手順書優先」（詳しくは §ガードレール設計の章）の一適用でもある——創意工夫より、まず手順書どおりに 1 回やり直す。

**一次記録**
`operations/playbook-cloud.md` の「制約」節（「計測系の異常は『故障』と断ずる前に手順書指定の呼び出し方で 1 回やり直す／2026-09-05 明文化」）。誤報とその影響の経緯は `company/decisions.md` 2026-09-04。

## 落とし穴6: 日付ドリフト — 連番や欠落から「今日」を推測すると過去に書き込む

**症状**
日報ファイル名や「第 N 営業日」のカウンタを、**既存ファイルの連番や前日の欠落から推測**して決めてしまい、実際の日付とずれた（過去日付で今日の日報を作ってしまう）。

**原因**
前日の営業が失敗して日報が飛んでいると、「欠落を埋めよう」という親切心が働き、欠番の日付で今日の成果を書いてしまう。2026-09-25 に実障害として発生した。日付を「推測」で決めた瞬間に、後段の検査（当日日報の存在チェックは `date +%F` と一致するファイルだけを合格にする）が 1 日ズレて失敗する連鎖も起きる。

**回避策**
- **日付は常にシステム時刻の実値（`date +%F`）を採用し、推測しない。** ファイル名・意思決定ログ・コミットメッセージ・曜日判定（週次の金曜判定など）はすべてこの 1 つの値に従う。
- **欠落日を過去日付で埋めない。** 前日が失敗していても、今日は今日の日付で書く。過去の日報は改変しない（追記のみ・改変禁止の原則）。
- カウンタ（稼働日数など）は推測せず、一次記録（`finance/kpi.json`）の値を +1 する。

**一次記録**
`operations/playbook-cloud.md` 実行手順 2 の「⚠日付ドリフト厳禁（2026-09-25 実障害）」。検査ガードは `daily-cloud.yml`（`date +%F` と一致する日報のみ合格）。

## まとめ — 6つの落とし穴に共通する 1 本の軸

6 件を並べると、共通項が見える。**「緑／成功／社内メモ／無人側の応答」を信用しすぎると事故になる**ということだ。

| # | 信用しすぎたもの | 代わりに信用すべきもの |
|---|---|---|
| 1 | cron の時刻・社内メモの「遅延は常態◯時間」 | その場で引く一次記録（`gh run list`） |
| 2 | 「push できるはず」という期待 | 権限の実体（GitHub App に workflows 権限は無い） |
| 3 | CI の success（緑） | 成果物が規格を満たすかの検査 |
| 4 | 無人側が返す 404 | 実ブラウザの到達性＋鮮度監視 |
| 5 | 「全件エラー＝外部故障」という結論 | 手順書指定の呼び出し方での 1 回の再現 |
| 6 | 連番・欠落からの日付推測 | `date +%F` の実値 |

無人運用の設計とは、要するに**「何を信用し、何を検査するか」を一つずつ決める作業**である。次章では、この軸をクラウドと手元 PC の二層構成に広げたときに生まれる競合と、その防ぎ方を扱う。

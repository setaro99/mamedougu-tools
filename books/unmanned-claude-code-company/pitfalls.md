## この章の目的
無人運用で**実際に起きた**事故を、症状→原因→回避策→一次記録の順で並べ、読者が同じ穴を踏まないようにする。

## 骨子（本文で書く落とし穴）
1. **cron は時刻どおりに来ない**: 指定時刻に対し実測の開始は数十分〜数時間ぶれた。**「+3.5〜4.5hが常態」という社内記述が、実は7月末の1週間だけの観測だった**という二次記述の誤りも実例として扱う（一次記録＝複数週の `gh run list` で訂正）。回避: 日付オフセット運用＋「遅くとも朝までに完了」の設計余裕。
2. **`GITHUB_TOKEN` は `.github/workflows/` を push できない**: GitHub App トークンに `workflows` 権限が無く、ワークフローファイルの新規作成/更新を含む push が**コミット単位で丸ごと拒否**される。怖いのは「そのファイルだけ落ちる」のではなく**その日の成果が全損**すること。実際に営業成果（日報・KPI・decisions）が全部 push できず消えた日がある。回避: ワークフロー変更は別ディレクトリに「案」として置き、権限のある経路（人の資格情報）で反映する。commit 前の自動退避ガードも用意。
3. **「success なのに何もしていない」**: セッションが正常終了（success）扱いなのに、その日の成果物（日報）が無い/変更ゼロの日があった。CI の緑は「仕事をした」ことを意味しない。回避: **当日の日報が存在し・サマリーを含み・一定バイト数以上**でなければワークフローを fail させ障害 Issue を発火するガード。
4. **ボット判定と到達性**: データセンターIP／非ブラウザUAからのアクセスが本番サービスにボット扱いされ、実際には公開中のページが 403/404 を返した（同時刻の実ブラウザでは 200）。回避: **無人側の 404 を『非公開の証拠にしない』**という規律と、鮮度監視（最後に実ブラウザで確認した日からの経過日数を警告）。
5. **計測系の誤報**: 指標取得を「手順書が指定する呼び出し方」と違う方法で試し、全件故障と誤報 → 誤った前提で方針を改訂してしまった。回避: **異常を『故障』と断ずる前に、手順書指定の呼び出し方で1回再現する**。
6. **（本で追加）日付ドリフト**: 連番や前日の欠落から今日の日付を推測して、過去日付で日報を作ってしまう事故。回避: 日付は常にシステム時刻の実値を採用し、推測しない。
